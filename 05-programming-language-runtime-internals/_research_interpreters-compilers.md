## 1. Key Mechanisms

### 1.1 Scanning / Lexical Analysis

**Forcing constraint:** The input is a linear stream of characters; the output must be a flat
sequence of tokens consumed by a parser that cannot backtrack across raw bytes.

**How it actually works (CI / clox scanner.c):**
Two raw C pointers `start` and `current` stride through the null-terminated source string in memory.
`start` anchors the beginning of the current lexeme; `current` advances one character at a time.
`makeToken()` computes the lexeme by slicing `[start, current)` — no allocation, just a length +
pointer stored in the `Token` struct. `match(expected)` implements one-character lookahead-and-consume
(conditional advance). `peekNext()` provides two-character lookahead for `!=`, `<=`, etc. without
consuming. Keywords are identified by a hand-rolled trie (`identifierType()` in scanner.c), not a
hash table — clox generates a switch/case cascade for each starting letter.

**jlox (Java) difference:** jlox's `Scanner.java` copies lexeme substrings into `String` objects on
every token; clox avoids this entirely by holding pointers into the original source buffer. This is
the key memory-efficiency forcing constraint for the C version.

**Ball / Monkey lexer:** A `Lexer` struct holds `input string`, `position int`, `readPosition int`,
`ch byte`. Identical two-pointer discipline but in Go. Tokens are Go structs `{Type, Literal}` where
`Literal` is a copied string (Go idiomatic; allocation cost accepted at lexer layer).

**Canonical source:**
- `github.com/munificent/craftinginterpreters/blob/master/c/scanner.c` (full clox scanner)
- `github.com/munificent/craftinginterpreters/blob/master/java/com/craftinginterpreters/lox/Scanner.java`
- CI book chapter: `github.com/munificent/craftinginterpreters/blob/master/book/scanning.md`

### 1.2 Parsing and AST Construction

**Forcing constraint:** Natural language grammar is ambiguous; operators have precedence and
associativity that must be encoded without ambiguity in the parse structure.

**Recursive Descent (jlox, Monkey):**
Each grammar rule becomes a method. The method for a rule at precedence P calls down to the method
for precedence P+1 for its sub-expressions. Left-recursion is eliminated by transforming `expr ->
expr op expr` into a loop inside the binary rule. The parse tree is materialized as Java/Go objects
(`Expr.Binary`, `Expr.Literal`, etc.). jlox uses code-generation (`tool/GenerateAst.java`) to emit
the Expr/Stmt class hierarchies — the only metaprogramming in the book.

**PrattTop-Down Operator Precedence) parser — clox:**
Vaughan Pratt (1973). Each token type has a `ParseRule{prefix, infix, Precedence}` entry in a
static lookup table (`rules[]` in compiler.c). `parsePrecedence(minPrec)` reads one token, calls its
`prefix` function (e.g., `number()`, `grouping()`, `unary()`), then loops: while the next token's
precedence >= `minPrec`, call its `infix` function (e.g., `binary()`, `call()`, `dot()`). No AST is
produced — bytecode is emitted directly during parsing (single-pass compilation).

**Why Pratt in clox but not jlox?**
jlox needs an AST for two passes (parse + resolve/bind before interpret). clox uses a single-pass
compiler that writes bytecode as it parses; an AST is unnecessary overhead. Pratt fits single-pass
because each token's parse action is independent and immediately produces code.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/book/parsing-expressions.md`
- `github.com/munificent/craftinginterpreters/blob/master/book/compiling-expressions.md`

### 1.3 AST Representation and the Visitor Pattern

**Forcing constraint:** A fixed set of node types must be processed by an open set of operations
(interpret, print, resolve) without modifying the node classes  new operation.

**jlox:** Uses the Visitor pattern. `Expr` is an abstract class with a nested `Visitor<R>` interface.
Each concrete node (`Expr.Binary`, `Expr.Literal`, etc.) implements `accept(Visitor<R> v)`. The
Interpreter, AstPrinter, and Resolver each implement Visitor, cleanly separating operations from
data. The class hierarchy is code-generated by `GenerateAst.java` — Nystrom acknowledges the Java
boilerplate problem (the "expression problem").

**Monkey (Ball):** Uses Go interfaces. `ast.Node` interface; `ast.Expression` and `ast.Statement`
embed Node. Each node type is a concrete Go struct. The evaluator switches on type assertion
(`switch node := node.(type)`) — no formal Visitor pattern, idiomatic Go.

- `github.com/munificent/craftinginterpreters/blob/master/book/representing-code.md`

### 1.4 Tree-Walk Interpreter and Environment Chain

**Forcing constraint:** Variable lookup must follow lexical scoping rules: inner scopes shadow outer,
and closures capture the binding at the point of function declaration, not call.

**jlox Environment chain:**
`Environment.java` is a linked list of `HashMap<String, Object>`. Each block scope creates a new
`Environment(enclosing)`. Variable lookup walks the chain via `enclosing.get()`. A function call
creates a new environment whose parent is the *closure environment* (the env at function declaration
time), not the call site — this is how lexical scoping is achieved.

**Two-pass resolution (Resolver.java):**
Before executing, jlox runs a static `Resolver` that walks the AST and computes for each variable
reference how many scope hops away the binding lives (`Map<Expr, Integer> locals`). At runtime,
`lookUpVariable()` uses this depth directly (O(depth) but depth-bounded). This avoids dynamic
lookup through potentially long chains and catches undefined variable errors statically.

**Monkey evaluator:** Same pattern — `Environment` struct has `store map[string]Object` and
`outer *Environment`. Closures capture `env` at function-literal evaluation time.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/java/com/craftinginterpreters/lox/Environment.java`
- `github.com/munificent/craftinginterpreters/blob/master/java/com/craftinginterpreters/lox/Resolver.java`
- `github.com/munificent/craftinginterpreters/blob/master/book/resolving-and-binding.md`

### 1.5 Bytecode and Chunk Structure

**Forcing constraint:** Tree-walk is slow (pointer-chasing across heap-scattered AST nodes, poor
cache locality, interface-dispatch overhead). A flat byte array of instructions is dense and
cache-friendly; the VM can decode and dispatch in a tight loop.

**clox Chunk struct (chunk.h):**
```c
typedef struct {
  int count; int capacity;
  uint8_t* code;       // flat bytecode array
  int* lines;          // parallel array: source line per instruction
  ValueArray constants; // constant pool
} Chunk;
```

**OpCode enum (partial):** `OP_CONSTANT`, `OP_ADD`, `OP_SUBTRACT`, `OP_MULTIPLY`, `OP_DIVIDE`,
`OP_NEGATE`, `OP_NOT`, `OP_EQUAL`, `OP_GREATER`, `OP_LESS`, `OP_PRINT`, `OP_POP`, `OP_GET_LOCAL`,
`OP_SET_LOCAL`, `OP_GET_GLOBAL`, `OP_DEFINE_GLOBAL`, `OP_GET_UPVALUE`, `OP_SET_UPVALUE`,
`OP_JUMP`, `OP_JUMP_IF_FALSE`, `OP_LOOP`, `OP_CALL`, `OP_CLOSURE`, `OP_CLOSE_UPVALUE`,
`OP_RETURN`, `OP_CLASS`, `OP_METHOD`, `OP_INHERIT`, `OP_INVOKE`, `OP_SUPER_INVOKE`.

**Monkey bytecode (Ball book 2):** `code.Instructions` is `[]byte`. Opcodes defined as `iota`
constants in `code/code.go`. Operands are big-endian 2-byte offsets into the constants pool.
No parallel lines array — Ball's Monkey VM omits line info for simplicity.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/c/chunk.h`
- `github.com/munificent/craftinginterpreters/blob/master/book/chunks-of-bytecode.md`

### 1.6 Stack-Based VM and Dispatch Loop

**Forcing constraint:** Register-based VMs need more complex instruction encoding and register
allocation. Stack-based VMs have simpler compilers at a modest per-instruction overhead cost (push/
pop); this tradeoff is correct for a pedagogical or scripting-language VM.

**clox VM (vm.h / vm.c):**
- `VM.stack[STACK_MAX]` — value stack. `stackTop` points one past the top element.
- `VM.frames[FRAMES_MAX]` — call frame array. Each `CallFrame` holds: `ObjClosure* closure`,
  `uint8_t* ip` (instruction pointer into the function's chunk), `Value* slots` (base pointer into
  the value stack for this frame's locals).
- `ip` is a **raw C pointer** into the bytecode array, not an index — dereferencing a pointer is
  faster than array indexing on most ABIs.
- The `run()` loop: `for(;;) { uint8_t instr = READ_BYTE(); switch(instr) { case OP_ADD: ... } }`
- `BINARY_OP` macro pops two values, applies the operator, pushes the result.
- On `OP_CALL`: a new `CallFrame` is pushed, `slots` points to the base of the new activation.
  No heap allocation per call — the stack is pre-allocated.

**Monkey VM (Ball book 2):**
- `[]object.Object` stack; `sp int` stack pointer.
- `globals []object.Object` (65536-slot slice for global variables).
- `frames []*Frame`; `Frame` holds `closure *object.Closure`, `ip int`, `basePointer int`.
- Dispatch: `switch opcode { case code.OpAdd: ... }` — Go type-switch.
- No GC code in Ball's VM; Go's GC handles heap objects.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/c/vm.h`
- `github.com/munificent/craftinginterpreters/blob/master/c/vm.c`
- `github.com/munificent/craftinginterpreters/blob/master/book/a-virtual-machine.md`

### 1.7 Value Representation: Tagged Union and NaN Boxing

**Forcing constraint:** A dynamically typed language must carry type info with each value at runtime.
The naive approach (struct with type tag + union) costs 16 bytes/value on 64-bit. Reducing this
improves cache utilization.

**Default (tagged union, value.h):**
```c
typedef struct {
  ValueType type;   // enum: VAL_BOOL, VAL_NIL, VAL_NUMBER, VAL_OBJ
  union { bool boolean; double number; Obj* obj; } as;
} Value;            // 16 bytes on 64-bit
```

**NaN boxing (`#ifdef NAN_BOXING`):**
IEEE 754 doubles use 52 fraction + 11 exponent + 1 sign bit. A "quiet NaN" is signaled by all 11
exponent bits set + fraction bit 51 set (QNAN = `0x7ffc000000000000`). The remaining 50 fraction
bits plus the sign bit give 51 bits of payload — enough for a 48-bit pointer (current x86-64
address space) or a small tag. clox uses: SIGN_BIT | QNAN = OBJ pointer (pointer in low 48 bits);
QNAN | TAG_NIL/TAG_FALSE/TAG_TRUE = nil/bools. All valid doubles are NOT NaN, so checking
`(value & QNAN) != QNAN` reliably identifies numbers. Result: `typedef uint64_t Value` — 8 bytes.
This is the same trick used by LuaJIT, JavaScriptCore (SpiderMonkey JSValue), and V8 (Smi tagging
variant). Attributed to David Gudeman's 1993 paper "Representing Type Information in Dynamically
Typed Languages" — Nystrom notes Gudeman called it "folklore".

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/c/value.h` (both representations)
- `github.com/munificent/craftinginterpreters/blob/master/book/optimization.md` (NaN boxing section)

### 1.8 Object Model and Heap Object Layout

**Forcing constraint:** The GC needs to traverse all heap objects; each object must be identifiable
by type at runtime without knowing its concrete type in advance.

**clox object.h:**
Every heap-allocated object begins with an `Obj` header:
```c
struct Obj { ObjType type; bool isMarked; struct Obj* next; };
```
`next` forms an intrusive singly-linked list of all heap objects (`VM.objects`). The GC uses
`isMarked`. Concrete types (ObjString, ObjFunction, ObjClosure, ObjUpvalue, ObjClass, ObjInstance,
ObjBoundMethod, ObjNative) embed `Obj` as their first field — the C "struct embedding" trick allows
safe casts between `Obj*` and any concrete type because `Obj` is at offset 0.

**ObjString** holds: `int length`, `char* chars`, `uint32_t hash` (cached FNV-1a).
**ObjFunction:** `int arity`, `int upvalueCount`, `Chunk chunk`, `ObjString* name`.
**ObjClosure:** `ObjFunction* function`, `ObjUpvalue** upvalues`, `int upvalueCount`.
**ObjInstance:** `ObjClass* klass`, `Table fields` (per-instance hash table).
**ObjClass:** `ObjString* name`, `Table methods`.

**Monkey object model (Ball):** A Go interface `Object{Type() ObjectType; Inspect() string}` —
no manual header embedding. The Go type system provides the polymorphism that C needs via manual
struct tricks. Ball's design is cleaner but hides GC from the learner (Go runtime handles it).

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/c/object.h`
- `github.com/munificent/craftinginterpreters/blob/master/book/strings.md`
- `github.com/munificent/craftinginterpreters/blob/master/book/classes-and-instances.md`

### 1.9 Closures: The Upvalue Mechanism (from Lua VM)

**Forcing constraint:** Locals live on the stack and are fast; closures must keep captured variables
alive after their enclosing scope exits. Allocating all locals on the heap is correct but slow.
Single-pass compilation means we cannot go back and fix emitted code when we later discover a
variable is captured.

**Upvalue design (credited to Lua VM team in clox chapter):**
An `ObjUpvalue` is an indirection cell with:
- `Value* location` — initially points into the stack slot of the captured variable.
- `Value closed` — the copy used after the stack frame is gone.
- `struct ObjUpvalue* next` — intrusive linked list sorted by stack address.

**Open upvalue:** `location` points into the live stack. Multiple closures capturing the same
variable share one upvalue (de-duplication in `captureUpvalue()` — walks `vm.openUpvalues` sorted
list to find or create).

**Closing upvalue (`closeUpvalues(last)`):** When a local variable goes out of scope, the VM calls
`closeUpvalues(slot)`. For every open upvalue whose `location >= slot`:
1. Copy `*upvalue->location` into `upvalue->closed`.
2. Redirect `upvalue->location = &upvalue->closed`.
3. Remove from the open list.

Now the upvalue is "closed over" — it lives independently of the stack. The closure still
dereferences `upvalue->location`, so no code change is needed. This is the key insight: the
indirection pointer transparently switches from stack to heap.

**jlox closures (simpler but slower):** `LoxFunction` captures the current `Environment` object at
declaration time. Every local is heap-allocated in a `HashMap<String, Object>` — no stack
optimization. This is why jlox closures are correct but jlox is ~72x slower than C on `fib(40)`.

**Monkey closures (Ball book 2):** `object.Closure{Fn *CompiledFunction, Free []object.Object}`.
`Free` is the slice of captured values. The compiler resolves free variable references and emits
`OpGetFree`/`OpSetFree` instructions.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/c/vm.c` (`captureUpvalue`, `closeUpvalues`)
- `github.com/munificent/craftinginterpreters/blob/master/c/object.h` (`ObjUpvalue`, `ObjClosure`)
- `github.com/munificent/craftinginterpreters/blob/master/book/closures.md`

### 1.10 Garbage Collection: Tri-Color Mark-and-Sweep

**Forcing constraint:** Managed languages need to reclaim unreachable objects. Reference counting
fails on cycles. Stop-the-world mark-and-sweep is simplest to implement correctly and is sufficient
for a scripting VM.

**Algorithm (clox, memory.c):**
Three phases:
1. **Mark roots:** Push all directly reachable roots onto the `grayStack` (global vars, stack
   values, open upvalues, compiler roots). `markObject()` sets `isMarked = true` and adds to gray.
2. **Blacken gray objects:** `traceReferences()` pops each gray object and marks all objects it
   references (ObjClosure → upvalues → function → constants; ObjClass → methods; ObjInstance →
   fields). Marked objects that are processed become "black" (marked + no longer gray).
3. **Sweep:** `sweep()` walks `VM.objects` linked list; frees all unmarked objects; clears marks
   on surviving objects for the next cycle.

**Tri-color invariant (Dijkstra):** White = not yet seen. Gray = seen but references not yet
traced. Black = seen and all references traced. The invariant: no black object points directly to
a white object. This invariant is maintained by adding referenced objects to gray before making
anything black.

**When to collect:** `reallocate()` triggers `collectGarbage()` when `vm.bytesAllocated > vm.nextGC`.
After each GC: `vm.nextGC = vm.bytesAllocated * GC_HEAP_GROW_FACTOR` (= 2). This is a heuristic
(doubles the threshold after each collection).

**String table and GC:** `vm.strings` is a hash set of interned strings. During sweep, dead strings
are also removed from `vm.strings` (`tableRemoveWhite()`), otherwise the table would hold dangling
pointers to freed memory. This is a subtle correctness constraint.

**Monkey / Ball:** No GC chapter — Ball explicitly delegates to Go's GC. This is a gap for learners
who need to understand GC mechanics.

### 1.11 String Interning and Hash Tables

**Forcing constraint:** String equality via `memcmp()` is O(n). Interning guarantees that equal
strings are the same heap object, making equality O(1) pointer comparison.

**Implementation (clox):**
`vm.strings` is a `Table` (open-addressing hash table with linear probing). Every new string is
looked up in `vm.strings` via `tableFindString()` before being allocated — if found, the existing
pointer is returned. After interning, `string == string` comparisons reduce to pointer equality.

**Hash function:** FNV-1a (Fowler–Noll–Vo). For each byte: `hash ^= byte; hash *= 16777619`.
The hash is stored in `ObjString.hash` and computed once at string creation.

**Hash table open addressing:** Buckets are a flat array. Collision resolution: linear probing
(advance one slot at a time, wrap around). Load factor threshold: 75% — when `count > capacity * 3 / 4`,
the table is grown by 2x and all entries rehashed. Tombstones mark deleted slots.

**Canonical sources:**
- `github.com/munificent/craftinginterpreters/blob/master/book/hash-tables.md`
- `github.com/munificent/craftinginterpreters/blob/master/c/table.c`
- `github.com/munificent/craftinginterpreters/blob/master/book/strings.md` (interning section)
- FNV-1a specification: `http://www.isthe.com/chongo/tech/comp/fnv/` (cited by Nystrom)

## 3. Why It's This Way — Constraints and Tradeoffs

| Design decision | Forcing constraint | Tradeoff accepted |
|---|---|---|
| **Two-pass jlox (parse + resolve)** | Static scope resolution requires knowing all variable depths before runtime | Extra pass, more code; buys O(1) variable lookup at runtime |
| **Single-pass clox compiler** | Memory pressure in C; no GC for the compiler's intermediate structures | Cannot resolve forward references; language must be designed to avoid them (Lox is) |
| **Pratt parsing for clox, recursive descent for jlox** | clox needs no AST (direct bytecode emission); jlox needs AST for Resolver pass | Pratt is harder to explain but faster to compile; recursive descent is easier to teach |
| **Stack-based VM (not register)** | Simpler compiler (no register allocation); easier to teach | More push/pop instructions per operation vs. register VM (e.g., Lua 5.x) |
| **Intrusive Obj linked list for GC** | No separate allocator or object map; trivial to add new heap types | Stop-the-world; list traversal is O(n) live objects; no compaction |
| **Upvalue indirection (from Lua)** | Stack locals must stay on stack until they escape; single-pass compiler cannot retroactively heap-allocate | Two code paths (stack / heap) in one object; extra pointer indirection for closed-over access |
| **String interning** | String equality needed for hash table keys and identifiers | Interning cost paid once at allocation; all subsequent comparisons O(1) |
| **NaN boxing (optional)** | 16-byte tagged union causes more cache misses than 8-byte NaN | Loses portability to platforms with unusual pointer widths; code complexity |
| **Go runtime GC in Monkey** | Ball's book focuses on interpreter/compiler construction, not GC | Students don't see GC implementation; must use CI for that |

## 4. Common Misconceptions to Preempt

1. **"Lexing and scanning are separate phases."** Modern interpreters (including both CI and Ball's
   Monkey) merge these into one pass. "Scanning" and "lexing" are now interchangeable terms.

2. **"Pratt parsers are only for expressions."** A Pratt parser handles all prefix and infix
   operators. Statements are handled by calling specific parse functions from the top-level
   `declaration()` function; the Pratt table handles operator expressions within them.

3. **"The AST is always built before execution."** jlox and Monkey (book 1) build an AST and then
   evaluate it. clox and Monkey (book 2) compile directly to bytecode — no AST exists at runtime.
   These are distinct execution strategies, not variants of the same thing.

4. **"Closures copy variables."** clox closures (and Ball's book-2 closures) capture *references* via
   upvalues or free-variable slots, not copies. Mutating a captured variable through any closure that
   shares its upvalue is visible to all closures that share that upvalue. jlox closures also capture by
   reference (the Environment object is shared).

5. **"The GC runs in the background."** clox's GC is stop-the-world — it is triggered synchronously
   inside `reallocate()` and pauses the VM for the full mark-and-sweep cycle. There is no
   incremental or concurrent GC in the book's implementation.

6. **"NaN boxing is only a trick — no production language uses it."** JavaScriptCore, SpiderMonkey
   (JSValue), LuaJIT, and MicroPython all use NaN boxing or pointer tagging variants in production.

7. **"String interning makes string creation slow."** The hash is O(length) at creation, but that
   cost is often paid anyway for the hash table insert. Lookup in `vm.strings` is O(1) expected.
   The win is on comparison and hash-table key lookup, which happen far more often than creation.

8. **"Ball's book is about the same thing as Crafting Interpreters."** Book 1 (interpreter) covers
   lexer/parser/tree-walk evaluator in Go — same territory as CI Part II (jlox). Book 2 (compiler)
   adds bytecode and a stack VM — same territory as CI Part III (clox), but without GC and without
   the C systems-programming concerns. The books are complementary, not redundant.

## 5. Best Build-Your-Own Targets

### Tier 1 — Mandatory for understanding (directly from source cluster)
- **Implement jlox (CI Part II) or Ball's Monkey interpreter:** The full pipeline: lexer → recursive-
  descent parser → AST → tree-walk evaluator with environment chain + closures. Suitable for any
  language (Go, Python, Rust, TypeScript). ~2,000 LOC in Go. The single clearest build target for
  understanding lexing, parsing, scope, and the Visitor pattern.
  - Source: CI chapters 4–13 (Scanning → Inheritance) + Nystrom's jlox in Java
  - CodeCrafters "Build Your Own Interpreter" track (Lox-compatible)

- **Implement clox (CI Part III):** Full bytecode compiler + stack VM in C: Pratt parser, Chunk,
  OpCode, Value, callframe, upvalues, tri-color GC, string interning, hash tables, classes.
  ~3,000 LOC in C. The single best target for understanding compiler + VM internals, GC, and NaN
  boxing. Most demanding but most complete systems-level build.
  - Source: CI chapters 14–30 + munificent/craftinginterpreters/c/

### Tier 2 — Valuable extensions
- **Add a Pratt parser to your tree-walk interpreter:** Replace recursive descent with a Pratt table;
  observe how new operators can be added by editing the table without restructuring the grammar.
- **Add NaN boxing to clox:** Change `#define NAN_BOXING` and verify the Value macros in value.h;
  benchmark against tagged union. Teaches IEEE 754 internals concretely.
- **Add a mark-sweep GC to Monkey (book 2):** Ball punts on GC; implementing tri-color mark-sweep
  on top of the Monkey VM closes the gap and applies the CI GC chapter to a Go codebase.
- **Implement Ball's Monkey compiler + VM (book 2):** Adds bytecode, constants pool, closures as
  free-variable arrays, frames — in Go. Easier systems-programming overhead than clox.

### Tier 3 — Stretch / cross-cutting
- **Add a JIT stub:** After clox is working, replace `OP_ADD` for doubles with a call to a
  machine-code stub allocated in an mmap'd RWX page. Bridges interpreter → JIT concepts.
- **Port clox to another language (Rust/Zig):** Forces understanding of every lifetime and ownership
  decision. The Obj linked list and GC marking are particularly illuminating in Rust.

## 6. Open Questions / Where Sources Disagree

1. **Pratt vs. recursive descent for a production interpreter:** CI uses Pratt for clox specifically
   because clox is single-pass. Ball's Monkey (book 1) uses recursive descent with explicit
   precedence climbing. The books implicitly disagree on which is "better for teaching" — CI
   presents Pratt as superior, Ball presents recursive descent as more readable.

2. **Stack VM vs. register VM tradeoff for scripting languages:** CI explicitly argues stack VMs are
   simpler to compile for. Lua 5.x moved from a stack VM (4.x) to a register VM precisely to reduce
   instruction count and improve performance. Neither book discusses register VMs; the Dragon Book
   and Lua 5.x internals papers are needed to resolve this.

3. **GC strategy at scale:** clox implements the simplest correct GC — stop-the-world mark-sweep.
   Real scripting language GCs (CPython refcount+cyclic collector, V8 generational, LuaJIT's GC)
   are substantially more complex. CI explicitly scopes out generational GC, incremental GC, and
   compacting GC as future work. See "The Garbage Collection Handbook" (Jones et al.) for the full
   design space.

4. **Single-pass compilation limits:** clox's single-pass compiler cannot handle forward references
   (e.g., `goto` targets, mutually recursive functions defined in arbitrary order). CI acknowledges
   this as a Lox language design choice. Production languages use a separate parse + lower pass.
   Ball's books also skip this problem. The tradeoff is underdiscussed.

5. **String representation:** clox uses length + char* (C string + NUL for printf compat).
   Ball's Monkey uses Go native strings (immutable, length-prefixed, UTF-8). The book does not
   address Unicode, grapheme clusters, or the `String.chars()` vs `String.codepoints()` distinction
   — a real gap for anyone building a production language.

6. **Ball's GC omission:** "Writing a Compiler in Go" has no GC chapter — Go's runtime handles it.
   Students who read Ball but not CI may not realize GC is a required component of a
   production interpreter. This is a significant pedagogical gap in the Ball source cluster.

7. **NaN boxing portability:** CI's NaN boxing assumes 64-bit pointers that fit in 48 bits (current
   x86-64 hardware). ARM64's top-byte ignore (TBI) feature complicates this. The book does not
   address pointer authentication (PAC) on Apple Silicon. [UNVERIFIED — Apple Silicon TBI/PAC
   interaction with NaN boxing not verified in CI errata or issues]
